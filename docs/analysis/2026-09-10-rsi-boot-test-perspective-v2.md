# RSI Adaptive Gateway — 测试工程师用户视角分析

> 版本：v0.2 | 日期：2026-09-10
> 视角：测试工程师（作为 RSI 网关的日常用户）
> 基于：RSI Adaptive Gateway v0.5 PRD / Spec / Plan 文档

---

## 写在前面

本文档从一个测试工程师的视角出发，分析 RSI Adaptive Gateway 作为一个**通用的 LLM 编排网关**，
在已经内置 Test Engineer 角色能力的前提下，能为我的日常工作带来什么价值，
以及这个框架对于测试团队而言是否值得推广。

> 核心认知：RSI 不是一个"测试工具"，而是一个**让 AI 更懂我的网关**。
> 它内置的 test 角色配置，让我可以像开发者和产品经理一样，
> 在同一个网关中获得贴合自己岗位需求的 AI 辅助。

## 1. 作为测试工程师，我的一天怎么用 RSI

### 1.1 早晨：测试用例生成（test_gen）

场景：新接口文档发布，需要写 CRUD 测试
操作：在 IDE 中粘贴接口定义，调用 rsi_query，设置 role=test, intent=test_gen

网关处理流程：
1. 意图识别 → test_gen
2. 加载 Test Engineer 策略 → 路由到 GPT-4o，使用 test_gen.jinja2 模板
3. 知识检索 → 检索项目测试规范、历史测试用例模式
4. 组装提示词 → 包含接口定义 + 项目测试规范 + 历史模式
5. 调用模型 → 流式返回测试用例
6. 后处理 → 按 test 角色格式渲染（detailed 风格，5 条建议）
7. 质量评估 → 按 test 角色权重（accuracy=0.4 优先）

输出效果：
- 基础 CRUD 正向流程：可用，节省约 40% 模板代码
- 边界条件：标记为"低置信度"，提醒人工补充
- 断言语句：按项目测试规范风格生成
- 附带来源："参考了 test_spec.md 第 3 节命名规范"

### 1.2 上午：测试代码审查（test_review）

场景：同事提交了测试 PR，需要审查测试代码质量
操作：选中测试代码段，调用 rsi_query，role=test, intent=test_review

网关输出：
- 覆盖率分析：哪些路径未覆盖、哪些断言薄弱
- 规范检查：命名是否符合项目约定、是否有冗余代码
- 改进建议：具体的修改方案
- 质量评分：按 test 权重计算（accuracy 占 0.4）

### 1.3 下午：Bug 分析辅助（bug_analyze）

场景：线上 bug，需要快速定位根因
操作：粘贴错误日志 + 相关代码，调用 rsi_query，role=test, intent=bug_analyze

网关输出（结合知识库中的历史 bug 记录）：
- 根因推测：基于相似 bug 模式
- 复现步骤建议
- 修复验证要点
- 关联的历史 bug："类似问题在 2026-03 出现过，根因是……"

### 1.4 日常：项目文档问答

场景：不清楚某个模块的测试环境配置
操作：直接提问，role=test

网关自动优先检索测试相关的知识条目（domain=test_environment, test_framework），
而非通用文档。

## 2. RSI 对测试工程师的价值分析

### 2.1 直接价值（开箱即用）

| 能力 | 对我的帮助 | 依赖 Phase |
|------|-----------|-----------|
| test_gen 意图 | 生成测试用例模板，节省 30-40% 编写时间 | P1 M2（基础支持）→ P2（完善） |
| test_review 意图 | 辅助测试代码审查，发现遗漏场景 | P2 |
| bug_analyze 意图 | 结合知识库分析 bug，减少排查时间 | P2（知识库）→ P3（学习闭环） |
| 角色感知知识检索 | 优先返回测试相关文档，避免信息噪声 | P2 |
| test 角色质量评估 | 按 accuracy 优先的评分标准，更贴合测试关注点 | P3 |
| test 角色格式化 | detailed 风格输出，更适合测试场景的步骤式展示 | P2 |

### 2.2 协作价值（团队使用）

- **同一网关，不同视角**：开发查代码、测试写用例、产品写文档——共享项目级上下文，但各自获得角色定制输出
- **知识库共建**：我导入的历史 bug 记录，开发 review 代码时也能参考
- **统一成本管控**：团队共用 API Key，按角色独立审计 token 消耗
- **学习闭环共享**：我的反馈（如频繁修改测试命名风格）会被系统学习，新生成的用例自动适配

### 2.3 长期价值（随着使用增长）

| 使用阶段 | 价值提升 |
|----------|----------|
| 第 1 周 | 基础模板生成，节省约 30% 用例编写时间 |
| 第 1 个月 | 知识库积累后，回复越来越贴近项目上下文 |
| 第 3 个月 | 学习闭环生效，策略和模板持续优化 |
| 第 6 个月 | 系统形成团队特有的测试知识资产 |

## 3. 设计合理性评估

### 3.1 角色设计：内置但不过度

RSI 没有把 test 角色做到代码级别硬编码，而是通过配置注册的方式：
- config/roles/test.yaml 定义意图规则
- config/role_templates/test_gen.jinja2 等模板
- quality_rubric.yaml 中 test 角色的 quality 权重
- response_format.yaml 中 test 角色的格式化配置

这意味着：
- **新角色扩展不需要改代码**——如果我想再加一个 performance_test 角色，只用加配置
- **没有 test 角色的团队**也不会受影响——走通用模式，照样能用

### 3.2 意图覆盖：基础可用，依赖后续 Phase

| 测试意图 | P1 M1 | P1 M2 | P2 | P3 | P4 |
|----------|-------|-------|----|-----|-----|
| test_gen | — | 基础支持 | 完善 | ✓ | ✓ |
| test_review | — | — | ✓ | ✓ | ✓ |
| bug_analyze | — | — | ✓ | ✓ | ✓ |
| test_data | — | — | — | ✓ | ✓ |
| coverage_check | — | — | — | ✓ | ✓ |

**关键发现**：测试角色的核心能力集中在 Phase 2 之后。Phase 1 M1 测试工程师只能用通用模式。
这意味着早期项目（前 4-5 周）测试团队的实际收益有限——但这是所有非开发角色的共性，不是设计缺陷。

### 3.3 质量评分：test 角色权重合理

当前设置的权重 accuracy=0.4, relevance=0.3, actionability=0.3 对测试场景合理——
测试用例的准确比生成速度更重要。建议后续增加请求级权重覆盖以支持灵活调整。

### 3.4 反馈机制：隐式信号的质量

测试场景下反馈信号天然带有噪声：
- 一个被"修改"的测试用例不一定代表生成的差——可能只是命名风格偏好
- 一个直接"采纳"的用例也不一定真的好——可能只是测试时间紧没细看

RSI 的隐式反馈设计如果只跟踪"采纳/修改"二元信号，在测试场景下的信噪比堪忧。
建议关注差异分析的深度：比较修改前后的 diff，提取实际改进点而非仅记录"被修改了"。

## 4. 这个框架能否推广到测试团队？

### 4.1 适合的团队画像

| 团队类型 | 适配度 | 说明 |
|----------|--------|------|
| 有 SDET 的团队 | 高 | SDET 可以自定义测试意图和模板，最大化价值 |
| 自动化测试团队 | 中高 | 测试用例生成和 review 价值高，需要有人初始化知识库 |
| 手工测试团队 | 低 | ROI 较低，核心价值来自知识库而非模板生成 |
| 小团队（< 5 人） | 中 | 轻量模式 SQLite + 文件索引快速启动，但冷启动成本相对高 |

### 4.2 推广建议

不要一上来就让整个测试团队用。建议分三步走：

**Step 1 — 探路者（前 2 周）**
- 1 名 SDET 或技术能力强的测试工程师先行试用
- 配置 test 角色意图和模板
- 导入已有测试文档到知识库
- 聚焦 test_gen 场景，评估模板节省效率

**Step 2 — 深耕（1-2 个月）**
- 基于探路者的反馈优化模板和知识库
- 扩展到 test_review 和 bug_analyze 场景
- 开始收集隐式反馈

**Step 3 — 推广（3 个月+）**
- 知识库内容丰富后，向全体测试团队开放
- 分享最佳实践和模板
- 持续评估 ROI

### 4.3 测试团队需要投入什么

| 投入项 | 说明 | 工作量 |
|-------|------|--------|
| 测试知识库初始化 | 导入历史 bug、测试规范、接口文档 | 2-3 人天（一次性） |
| 测试模板定制 | 调整 test_gen.jinja2 以匹配项目风格 | 0.5-1 人天 |
| 反馈标注 | 初期需要显式反馈以加速学习 | 每次操作 < 5 秒 |
| 持续维护 | 知识库更新、模板优化 | 每迭代 0.5 人天 |

## 5. 已满足和期望补充的能力

### 5.1 已满足的

- test_gen 和 test_review 意图覆盖了核心场景
- 角色感知知识检索让回复更相关
- 质量评分按 accuracy 加权，符合测试关注点
- 角色独立反馈统计，我的数据不会被开发的数据稀释
- 隐式反馈跟踪采纳率，让系统自己学习

### 5.2 期待未来补充的

- **确定性模式**：deterministic=true 参数让 test_gen 的输出可复现，方便回归验证
- **批量测试数据生成**：基于 Pydantic 模型自动生成边界值组合
- **测试管理工具集成**：Jira/Xray 等工具直接通过 MCP 工具操作

### 5.3 一个测试工程师的希望清单

1. Phase 2 尽快上线：知识库是我最想要的能力
2. 手动初始化知识库时提供文档批量导入脚本
3. test_gen 支持指定测试框架（pytest / junit / unittest）
4. 输出中显式标注置信度，让我判断哪里需要重点审查
5. 和 CI/CD 集成：每次构建后自动分析测试日志
6. 支持 YAML/JSON 格式的测试数据导出

## 6. 总体评价

### 核心结论

RSI Adaptive Gateway 作为一个**通用的 LLM 编排网关**，在 v0.5 版本中通过内置
Test Engineer 角色，已经具备了为测试工程师提供实际价值的基础。
它不是一个"测试工具"，但**测试工程师用它的体验，和开发者一样顺畅**——
这是设计成功的标志：通用不等于不适合特定角色。

| 维度 | 评分（1-5） | 说明 |
|------|------------|------|
| 角色覆盖完整性 | 4/5 | 测试角色已经内置，不需要二次开发 |
| 核心场景贴合度 | 4/5 | test_gen / test_review / bug_analyze 覆盖了日常工作 |
| 冷启动友好度 | 3/5 | 需要手动初始化知识库，建议提供更丰富的种子脚本 |
| 与团队协作的契合度 | 5/5 | 同一网关多角色协作是最大亮点 |
| 推广可操作性 | 4/5 | 分三步走的策略清晰，投入产出比可预期 |
| 长期扩展潜力 | 4/5 | 角色插件化架构让测试团队可以自定义扩展 |

### 一句话总结

> 作为测试工程师，我不会因为 RSI 的定位是"通用网关"而觉得它不适合我。
> 恰恰相反，**正因为它是通用的、可配置的、角色感知的**，
> 我才能在同一个框架中，获得贴合测试岗位、同时与开发和产品协作无间的 AI 辅助体验。
> 它不需要变成"测试工具"——它只需要**理解我**。
