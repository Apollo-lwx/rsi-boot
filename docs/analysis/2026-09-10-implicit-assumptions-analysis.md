## 背景

RSI Adaptive Gateway 定位为"通用的 LLM 编排网关"，不限于特定角色或领域。
但当前 v0.3 的三份核心文档（PRD / Spec / Plans）中存在多处"默认用户是开发者"的隐含假设，
这些假设若不加修正，会导致系统在服务测试、产品、运营等其他角色时出现设计排斥。

本报告逐项识别这些假设，并给出修正方向。

---

## 一、PRD 中的隐含假设

### H1：核心场景只覆盖开发链路

| 位置 | PRD Section 3「核心场景」 |
|------|--------------------------|
| **原文** | 场景 A：代码开发辅助（核心场景）- 场景 B：项目文档问答 - 场景 C：团队统一 AI 接入 |
| **隐含假设** | 用户的日常工作产出是代码，核心价值在"写代码时给建议" |
| **影响** | 测试人员（编写用例/分析 Bug）、产品经理（写 PRD/分析需求）找不到自己的场景入口 |
| **修正方向** | 场景描述保持抽象（"工作产出辅助"而非"代码辅助"），每个场景补充多角色示例 |

### H2：用户画像只有技术偏好

| 位置 | PRD Section 4«功能优先级» - user_profiles |
|------|------------------------------------------|
| **原文** | preferences: code_style, response_lang, detail_level |
| **隐含假设** | 用户的核心偏好围绕「代码风格」和「技术细节」| 
| **影响** | 测试人员关心的是测试框架偏好（pytest vs jest）、报告格式；产品经理关心的是文档详细度、输出格式 |
| **修正方向** | 将 code_style 改为角色无关的偏好命名空间，支持 role-specific 扩展 |

### H3：成功指标偏向代码产出

| 位置 | PRD Section 5「成功指标」 |
|------|--------------------------|
| **原文** | 代码采纳率 > 60%，上下文相关性评分 > 0.8 |
| **隐含假设** | 系统的主要产出是代码，可以被"采纳" |
| **影响** | 测试人员的产出（用例、报告）和产品经理的产出（文档、分析）无法用"采纳率"衡量 |
| **修正方向** | 按角色定义不同的成功指标模板，系统可配置 |

### H4：MoSCoW 未包含角色基础设施

| 位置 | PRD Section 4「功能优先级」 |
|------|---------------------------|
| **隐含假设** | 用户角色是固定的（开发者），不需要在系统中管理角色 |
| **影响** | 多角色切换、角色偏好隔离、角色插件等基础设施功能缺失 |
| **修正方向** | 增加「多角色支持」为 P1 基础设施需求 |

## 二、Specs 中的隐含假设

### H5：意图识别硬编码为开发意图

| 位置 | Spec Section 3.6（角色意图映射；v0.2 注：初稿误标为 §3.1，9 意图实际定义于 §3.6） |
|------|------------------|
| **原文** | 角色意图映射中的 9 种开发者意图：explain, debug, refactor, testing, code_gen, documentation, code_review, devops, howto |
| **隐含假设** | 所有用户的请求都可以归入这 9 类开发者意图 |
| **影响** | 测试人员的"生成用例"需求归入 general/product_manager 的"写 PRD"归入 general，精度下降 |
| **修正方向** | 意图识别改为插件化注册，预置 dev/test/pm 三套基础分类，支持自定义 |

### H6：反馈模型只支持「采纳/修改/拒绝」

| 位置 | Spec Section 2.1 - FeedbackAction |
|------|-----------------------------------|
| **原文** | ACCEPTED, MODIFIED, IGNORED, REJECTED, COPIED, APPLIED |
| **隐含假设** | 用户的交互模式是「接受建议 → 按 Tab 采纳」| 
| **影响** | 产品经理参考 AI 的分析来完善自己的文档（参考而非采纳），测试人员参考用例思路后自己重写，都产生弱反馈信号 |
| **修正方向** | 增加「REFERENCED」动作，表示用户参考了但未直接使用 |

### H7：知识条目没有领域/角色字段

| 位置 | Spec Section 2.2 - knowledge_items 表 |
|------|---------------------------------------|
| **原文** | content, content_type, language, tags, source |
| **隐含假设** | 知识是通用的文本/代码，不需要区分属于哪个角色或领域 |
| **影响** | 测试规范（如 Mock 策略）、产品规范（如需求模板）混在一起，检索精度下降 |
| **修正方向** | 增加 role/domain 字段，支持自定义 metadata schema |

### H8：质量评估偏向代码输出

| 位置 | Spec Section 3.5 |
|------|------------------|
| **原文** | 三维度评分：相关性(0.5)+完整性(0.3)+格式合规(0.2)，其中完整性检查 code intent→含代码块 +50% |
| **隐含假设** | 高质量响应的标志是包含代码块 |
| **影响** | 对测试场景（测试用例列表）和产品场景（PRD 大纲）的评分可能偏低 |
| **修正方向** | 评分 rubric 可配置，按角色/意图选择不同的评估模板 |

### H9：RSIResponse 没有角色上下文

| 位置 | Spec Section 2.1 - RSIResponse |
|------|--------------------------------|
| **隐含假设** | 响应是自包含的，不需要知道用户角色来渲染 |
| **影响** | 同一请求对不同角色的最佳展示格式不同（开发者要代码块、测试要表格、产品要结构化文档） |
| **修正方向** | 角色信息传入后处理，支持角色感知的响应格式化 |

## 三、Plans 中的隐含假设

### H10：Phase 1 验收标准只有开发者场景

| 位置 | Plans Phase 1 交付检查清单 |
|------|--------------------------|
| **隐含假设** | Phase 1 只要满足开发者就能交付 |
| **影响** | 非开发者用户在 Phase 1 无法验证系统对自己的价值 |
| **修正方向** | 增加多角色验证场景（测试：生成测试用例 / PM：生成文档大纲）|

## 五、修正原则

1. **不改定位**：RSI 是通用网关，不专为某一角色设计
2. **角色是数据不是代码**：角色信息作为请求上下文传入，不硬编码到系统逻辑中
3. **预置 3 套模板**：内置 Developer / Test / PM 三套意图 + 偏好 + 模板配置，开箱即用
4. **可扩展**：第四角色通过配置而非代码实现，无需修改核心
5. **角色感知 = 可选增强**：系统在不感知角色时正常工作（兜底通用模式），感知角色后表现更好
